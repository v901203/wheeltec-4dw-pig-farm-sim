# LiDAR 傳統直行與巡邏控制

目前使用 LiDAR 與傳統閉迴路控制，巡邏狀態機管理主幹道及左右支線的行駛順序。控制器不讀取底盤 odom／IMU，也不需要載入模型。

[fsm_lidar_patrol.py](fsm_lidar_patrol.py) 是完整巡邏入口；[fsm_patrol.py](fsm_patrol.py) 保留獨立直行功能，兩個入口擇一執行。

## 完整巡邏

巡邏順序為：主幹道前進 → 路口置中 → 左轉 90° → 左支線前進到底 → 保持車頭方向倒退，穿過路口直到右支線底端 → 前進返回路口中心 → 右轉回主幹道 → 前往下一個路口。主幹道前方出現封牆時停車。

路口數使用設定檔的 `junctions`（目前為 3）。完成全部路口並回到主幹道後，進入 `FINAL_MAIN`：「支線巡邏完成，沿主幹道前進至終點」。此狀態不再辨識或進入新支線，仍須由 LiDAR 連續確認前方終點牆才進入 `DONE`；不會只因支線數達標就原地結束。若路口／端點尚未巡完就遇到主幹道封牆，停車並回報 `main_end_before_patrol_complete`，不算成功完成。更換世界時需同步確認路口數設定。

先依下節啟動 Gazebo，建議使用 `--lidar-only --rtf 1`。車輛應從預設起點、面朝主幹道前進方向開始。另一個終端執行：

```bash
cd /home/an/Desktop/4wd
source /opt/ros/humble/setup.bash
/usr/bin/python3 rl_pig_pen/fsm_lidar_patrol.py
```

執行前先停止 `fsm_patrol.py` 或鍵盤控制，確保只有一個速度發布者。巡邏控制不會自動重設車子；中途失敗後，需先確認原因並將車子恢復至適當的主幹道起始位置，再重新啟動。

此入口使用 [lidar_patrol_controller.py](lidar_patrol_controller.py) 管理路線，並使用現有路口幾何與牆線工具：

- 主幹道與支線以局部平行牆面修正方向、左右置中；倒車時反轉置中修正方向。
- 路口以四面牆的開口估計中心；90° 轉彎追蹤同一條進入走道的方向，避免誤選垂直走道。
- 首次確認路口仍需四面牆的開口。確認後，若完整開口辨識暫時失敗，可利用已量到的走道寬度及至少三面、分屬兩個方向的可見牆線追蹤中心；只有平行牆、配對不明確或位置／方向跳變時仍停止。追蹤不使用命令速度推算位置。
- 完整開口辨識若出現位置或方向跳變，不直接覆蓋原本路口；先以同一筆掃描的牆線驗證既有追蹤。若牆線結果連續且通過原安全檢查便採用，否則停止。時間中斷不能用這個機制略過。
- 置中接近目標時降低速度；若小幅越過中心，在 `junction_turn_centre_limit`（預設 0.15 m）範圍內以最高 0.05 m/s 倒退修正，仍檢查後方淨空。回到中心容許範圍且朝向對準、連續確認後才開始轉彎；超出回正範圍會停止。
- `CENTER`／`RETURN_CENTER` 現在代表轉彎準備：以 `junction_centre_tolerance`（目前 0.05 m）作為中心附近的圓形容許區域，第一次接近就可使用，不必先耗掉重試次數。這是前後與側向誤差合成後的總距離，不是兩個方向各允許 5 cm。區域內停止平移、對正走道方向，連續三筆確認位置與方向合格後，仍須通過旋轉淨空檢查才能轉彎。
- 區域外才繼續接近或重新定位：前後誤差小於 4 cm、側向誤差超過容許範圍時，保持走道朝向，以最高 0.05 m/s 後退，直到量到中心在前方 0.35 m，再低速重新接近。每次置中最多兩次重新接近，開始退開即計一次；不是整趟巡邏共用的次數。若仍需要第三次，先停車，連續三筆確認後回報 `centre_reposition_limit`；大幅越位、障礙、幾何中斷與狀態超時保護維持不變。
- 轉彎後並不直接視為成功進入走道。`ENTRY_LEFT`／`CROSS_REVERSE`／`EXIT_MAIN` 在前半段依路口幾何修正，進入深度達目標的一半且可辨識平行牆後，改以當前牆面修正方向與左右偏差。控制仍以約 3.44°、5 cm 為理想目標；尚未達理想值時降至 0.07 m/s。預設深度至少 0.9 m、雙側牆存在，且牆面方向誤差不超過 5°、牆面中心側偏不超過 12 cm，連續三筆便安全交接給直線沿牆控制繼續收斂。交接不再強制遠處的路口中心估計也維持 5 cm；只有 `EXIT_MAIN` 完成才增加路口數。
- 支線端點仍需同時符合近距離與橫向牆線條件。放寬轉彎前的位置精度，不會放寬車身、旋轉或前進／倒退煞停淨空。
- 不讀取 odom／IMU、世界座標或路徑點，也不使用命令速度積分或固定秒數判定動作完成。
- 僅處理新時間戳的掃描；重複資料停止輸出運動。接收間隔超過自適應暫停門檻時立即送零速度；時間倒退或追蹤跳變仍會鎖定停止。一般障礙淨空不足時保留原路線狀態等待，障礙移開且連續確認後自動恢復；疑似障礙已進入車體範圍仍鎖定失敗。
- 無效點（含單筆 `NaN`）或重複掃描先立即發布零速度，不把無效點當成真實零距離障礙。預設連續三筆新鮮、有效且可定位的掃描，通過原有安全與幾何連續性檢查才恢復；等待期間只更新已驗證的感測時間與幾何，不累加路線進度。監測程序重複發現接收間隔偏長不會清掉確認筆數；實際收到無效、重複或無法定位的掃描才中斷連續確認。
- 接收暫停門檻初始約 0.17 秒；取得至少三組有效掃描間隔後，以最近最多 16 組間隔的第 90 百分位估計，採 `1.5 × 間隔 + 0.02 秒`，上限 0.4 秒。無效或重複掃描不拿來學習延遲，監測仍每 0.1 秒執行。這讓穩定但較慢的模擬不再持續觸發原本固定門檻；啟動初期仍可能有一次暫停與恢復。
- 完全收不到資料時，超過自適應門檻（上限 0.4 秒）便停車，但不再於固定 0.5 秒直接終止巡邏。從門檻被跨越的時刻開始使用 `sensor_timeout`（預設 3 秒）作為同一次恢復期限；新掃描在期限內抵達仍須連續三筆有效、可定位且安全才恢復，超過期限則回報 `scan_receive_timeout`。即使監測回呼或下一筆封包延遲抵達，已經過的中斷時間也會計入期限，不能用新封包重設。這不是允許車子沿用舊指令行駛 3 秒。
- 感測時間戳與路口追蹤的最大間隔、位移及角度限制仍保留，逐筆驗證有效資料。巡邏 ROS 入口的前進／倒退煞停檢查同步採至少 0.5 秒反應時間（接收暫停上限加監測週期），而非沿用 1/12 秒；不把較慢掃描當成沒有額外風險。若超出接收上限或系統排程持續延遲，仍須改善負載，這不是硬即時或實車停車距離保證。
- 旋轉淨空依運動型態分開：原地轉向維持車身外接圓保護；前進或倒車同時修正方向時，依命令曲率，在反應、煞停及額外停止距離內逐段檢查車身矩形的弧形掃掠區域。朝遠離側牆的修正可繼續，會讓前／後車角掃向牆面的修正仍停止；診斷以 `sweep` 標示弧形掃掠觸發，不再把所有非零角速度都標為 `rotation`。
- 看不清走道或路口時先停車，持續無法完成狀態會判定失敗。計時器只用於資料監測／失敗保護，不用來判定轉彎完成。

障礙觸發行進保護時會先停車，反方向連續三筆確認安全後，以 0.05 m/s 反向退避，同一次事件最多嘗試一次。前進受阻就倒車，倒車受阻就前進；退避途中反方向受阻、姿態偏移或雷達異常，都立即停止。

- 路口模式保留原有幾何追蹤限制：量到約 0.10 m 便停止，須有足夠追蹤範圍，且不能只有側向掃掠命中。
- 普通走道的 `MAIN`／`FINAL_MAIN`／`LEFT_OUTBOUND`／`REVERSE_LEFT`／`RIGHT_OUTBOUND`／`RETURN_RIGHT`，沒有已取得路口追蹤時，改用淨空模式。`travel` 或 `sweep` 受阻都可嘗試反方向直線退避；仍需雙側走道可辨識且反向路徑安全。原指令的安全淨空恢復後停止；最多 4 秒感測時間便中止退避。這個上限是監測保護，不代表量到確切退避距離，日誌也不會宣稱量到 0.10 m。
- 退避停止與恢復原動作分開判斷。恢復需原方向更大的淨空及連續三筆確認：路口模式加入量測退避距離，淨空模式加入 0.20 m 保守退避裕量，再加 4 cm 遲滯，降低退遠後立刻又朝同一面牆前進的風險。這仍依賴命令速度／煞停假設，不是障礙移除辨識或實車位移保證；固定牆尚未確認為端點時可能繼續等待。

接近可能的端牆（前進方向牆面距離小於 0.85 m）會降至最高 0.07 m/s，角速度同比例縮小以保持曲率。左右支線即使已因障礙停車，仍持續辨識橫向端牆：連續三筆確認後才增加端點數，`LEFT_OUTBOUND → REVERSE_LEFT`，`RIGHT_OUTBOUND → RETURN_RIGHT`，下一筆掃描依返回方向離開。單一近點不算端點；感測暫停或重複掃描會中斷確認。一般障礙等待與退避不累加路線計數，只有確認支線端牆才增加端點數。

`rotation` 旋轉淨空不足只等待，不自行平移。若 `footprint` 表示有效回波已進入車體範圍，仍回報 `obstacle_clearance` 並鎖定失敗，不自動脫困。雷達無效、接收失聯或路口追蹤異常仍按各自故障處理，不能靠障礙恢復機制略過。日誌中的「障礙診斷」會保留觸發時速度命令、雷達點距離／角度及安全門檻。

若出現 `junction_geometry_lost`，診斷會列出幾何資料中斷秒數、最後一次有效中心位置及方向。可用幾何的來源會標示為 `four_openings`（完整開口辨識）或 `tracked_walls`（已確認路口的牆面追蹤）。

若出現 `scan_receive_timeout` 或 `scan_recovery_timeout`，停止診斷會列出最後接收資料的間隔／已過時間、恢復等待時間、已確認／所需筆數及最近觀測／驗證的掃描時間戳。前者表示接收間隔從安全暫停門檻起已超過完整恢復期限；後者表示收到無效、重複或無法定位的資料後，期限內仍未完成恢復確認。

若出現 `centre_reposition_limit`，診斷會列出中心總距離、前後／側向誤差、轉彎區域容許誤差、已用次數及原因。`retries_exhausted` 表示重新接近次數耗盡且仍在區域外需要修正，`lateral_out_of_bounds` 表示觸發重新定位時側偏超出回正範圍；兩者都不是障礙距離檢查失敗。進入走道的診斷另列出深度、幾何側偏、牆面方向與側偏，以及是否通過牆面交接條件。

若新辨識被拒絕，`rejected_geometry` 會保留前後中心座標、估計位移／轉角及門檻。成功改用當前牆線時來源為 `tracked_walls_after_rejection`；若牆線也無法支持連續位置，仍會回報 `junction_position_jump` 或 `junction_axis_jump`。

自動路線測試使用世界檔靜態射線與理想差速運動，已完成三個路口、六個支線端點至主幹道終點；另有使用者的 Gazebo 路口行駛回報。兩者都不能取代動態障礙、重複成功率與實車驗證。巡邏假設有可辨識的直角十字路口與封閉端牆；短距離退避不是繞障或動態改道。

## 原本直行腳本的控制方式與參數

控制器訂閱 `/scan`（`sensor_msgs/msg/LaserScan`），發布 `/cmd_vel`（`geometry_msgs/msg/Twist`）。

每次控制迴圈執行以下判斷：

1. 尚未收到掃描時，等待資料。
2. 前方 ±10° 扇區的最短距離小於 0.55 m 時，發布零速度。
3. 取左前 35°～65°、右前 −65°～−35° 扇區的最短距離，計算左右距離差。
4. 將牆線平行誤差與左右距離差組合成角速度，配合設定的巡航速度前進。

```text
center_error = forward_left - forward_right
angular_z = clip(1.4 × wall_parallel_error + 1.0 × center_error, -0.3, 0.3)
linear_x = clip(cruise_speed, 0, MAX_LIN)
```

平行誤差以弧度表示，距離差以公尺表示。牆線由 [lidar_geometry.py](lidar_geometry.py) 分別擬合，再配對平行牆面。

| 項目 | 目前值 | 設定位置 |
| --- | --- | --- |
| 巡航速度 `cruise_speed` | 0.2 m/s | [patrol_config.json](patrol_config.json) |
| 控制週期 `control_dt` | 1/12 秒，約 12 Hz | `patrol_config.json` |
| LiDAR 安裝偏角 `lidar_yaw` | 0 rad | `patrol_config.json` |
| 平行修正增益 `kp_heading` | 1.4 | `fsm_patrol.py` |
| 置中修正增益 `kp_center` | 1.0 | `fsm_patrol.py` |
| 直行時角速度上限 | ±0.3 rad/s | `fsm_patrol.py`，另受 `MAX_ANG` 限制 |
| 前方停車門檻 | 0.55 m | `fsm_patrol.py` |
| 共用速度上限 `MAX_LIN`／`MAX_ANG` | 0.5 m/s／0.6 rad/s | [navigation.py](navigation.py) |

設定檔固定從 `navigation.py` 同目錄的 `patrol_config.json` 載入；目前入口沒有自訂 `--config` 參數。修改後需重啟控制器。

`control_dt` 用於 ROS timer 排程。現有程式會讀取最新快取掃描，未做到每筆新掃描只控制一次，也沒有以計時器判定轉彎或路口置中完成的流程。

`junctions` 與 `turn_speed` 等欄位供完整巡邏使用，不會讓原本直行節點執行巡邏或轉彎。`start` 不會讓控制器自動重設車子；Gazebo 出生位置由 `launch_clean.sh` 的生成指令設定。

## 檢查發現與待改善項目

三項已重現問題已加入對應處理及自動測試。以下區分程式改善與仍需實測的部分；這次新增功能尚未完成 Gazebo 物理或實車驗收。

| 優先順序 | 問題與證據 | 影響／後續方向 |
| --- | --- | --- |
| 已改善 | 純左右偏移：新增有界限的退開與重新接近策略 | 測試涵蓋兩個置中狀態、左右各 10 cm 偏移、實際世界牆線擬合、後方障礙與重試／超時限制 |
| 已改善，實車前需驗證 | 串口轉接以單調時鐘檢查速度接收時間；預設超過 0.5 秒便持續送零速度 | 獨立於巡邏程序，但不保護轉接程序自身被強制終止、Xavier 斷電或串口斷線；仍需底盤 watchdog 與急停 |
| 已改善 | 感測暫停／恢復不再讓單筆無效點直接變成障礙失敗，且分開處理接收失聯與停車恢復期限 | 測試涵蓋低頻、接收抖動、模擬降速、重複監測、持續異常、轉彎中幾何連續性，以及無效點與真實近障礙同時出現；新版仍待 Gazebo 實測 |
| 中 | 中斷後沒有進度續接，也沒有障礙繞行 | `FAILED` 會維持停止；重新啟動會清空路口計數，不能當成從原地續跑 |
| 驗證 | 路口數來自設定、沒有地圖中的唯一路口辨識；終點以近距離橫向牆線判定 | 換場景、路口誤認及大型平面障礙仍需測試；不能把路口計數當作地圖定位 |

另外，安全煞停距離目前使用命令速度與預估反應時間；巡邏 ROS 入口至少預留 0.5 秒，但仍未驗證真實慣性、滑動、傳輸或排程延遲下的最壞停車距離。LiDAR-only 控制不必改用底盤回授，但實車仍需針對這些差異量測與驗證。

下一步在 Gazebo 實際執行新版完整路線及故障注入，再做重複巡邏統計。每回合至少保留最終狀態、路口／端點數、完成時間與失敗原因，並分別測試初始偏移、遮擋、動態障礙與低模擬速度。Xavier／實體車驗證前，先確認獨立停車保護。

## Xavier 速度接收逾時保護

[cmdvel_to_stm32.py](../scripts/cmdvel_to_stm32.py) 需作為獨立程序執行，且必須是實際通往底盤的速度介面，這項保護才會生效；`launch_clean.sh` 不會啟動它，Gazebo bridge 也不會自動獲得此保護。不要同時執行多個底盤速度轉接程序。

接收端採用單調時鐘與穩定時鐘計時器，不受 ROS 模擬時間暫停影響。預設 `command_timeout=0.5` 秒、10 Hz 檢查；逾時後在下一次計時回呼送出零速度並持續重送，只有新收到的有限數值命令才能恢復。實際反應時間仍受系統排程與串口傳輸影響，不是硬即時保證。啟動與正常關閉也會送零速度；寫入失敗會清除快取運動命令。

這不需 odom／IMU 或底盤程式修改，但不是實體急停替代品。轉接程序停止、整台 Xavier 失效或線路中斷時，它無法再送出停止封包，必須另外確認底盤原有的指令失聯保護。測試使用模擬串口，尚未驗證實體馬達停車距離。

## 未來工作：機器學習與碩士論文方向

以下為研究規劃，尚未實作或驗證，不屬於目前已完成的巡邏功能。保留現有 LiDAR 傳統控制作為比較基準，先統計完整路線的成功率與失敗原因，再選擇一項主要學習任務；不以加入模型本身作為成果，也不預設機器學習一定優於傳統方法。

### 可加入學習的位置

| 方向 | 模型負責的工作 | 預期研究問題 |
| --- | --- | --- |
| 局部控制修正（優先評估） | 在傳統線速度與角速度指令上加入受限修正量 | 能否改善路口置中、90° 轉彎與轉彎後交接，在偏移、滑動及延遲下的穩定性？ |
| 控制參數調整 | 依當下感測與狀態，選擇速度範圍、轉向及置中增益 | 能否減少不同路寬、車況與前進／倒退情境的人工調參需求？ |
| LiDAR 路口感知 | 估計路口是否存在、中心、走道方向與可信度 | 能否降低欄杆干擾、遮擋、假路口及位置跳變造成的誤判？ |

三個方向可分別發展，不建議第一階段同時更換感知與控制。若主要失敗來源是路口辨識錯誤，應優先改善感知；若幾何估計可靠但動作容易越位、振盪或偏離，則優先研究控制修正。學習感知可採監督式學習，不必使用強化學習。

### 建議主題：傳統控制結合殘差強化學習

殘差強化學習讓傳統控制提供基本動作，模型只學習補償量。初期將學習範圍限制在「路口置中 → 90° 轉彎 → 進入走道的短距離修正」，主幹道與支線長距離直行仍由傳統演算法處理。

```text
FSM 決定路線階段與允許的動作方向
                  ↓
傳統速度指令 ＋ RL 有限幅度修正
                  ↓
既有安全檢查：限速、障礙、感測有效性與失聯停車
                  ↓
底盤速度介面
```

路線順序、完成判斷及安全停止不交給模型取消；修正量須受當前狀態允許的動作方向與速度範圍限制。資料失效時仍停止，不能靠模型猜測繼續行駛。保留安全檢查不等於已證明整個學習系統安全，仍需針對延遲、煞停及介入情境驗證。

候選輸入包括 LiDAR 特徵、FSM 狀態、中心前後／左右誤差、相對走道方向誤差、幾何可信度、有效性標記、最近幾筆掃描及前一次實際送出的速度指令。輸入維度依任務設計，不預先固定為 49 維。命令紀錄不是實際車速，不能當成底盤回授或真實位移。

訓練目標可兼顧位置與方向誤差收斂、操作完成、時間成本和動作平順度，並記錄碰撞及安全介入；不能只用前進距離或角速度當作獎勵。訓練時也應包含部署使用的安全檢查，分別記錄模型提出的指令與最後送出的指令，避免把安全保護的效果誤認為模型本身的能力。

這類混合方式已有 [Residual Reinforcement Learning for Robot Control](https://arxiv.org/abs/1812.03201) 等研究。因此，「傳統指令加上模型修正」本身不是新的貢獻；應研究 LiDAR-only、前進與倒退混合的窄走道巡邏，在特定不確定性下的有效性與限制。

若希望先縮小實作範圍，可改以學習調參為主題，但保持安全門檻不被模型放寬。[APPLR](https://www.cs.utexas.edu/~pstone/Papers/bib2html/b2hd-icra21-xu.html) 已研究以強化學習選擇傳統導航參數，可作為相關工作與比較設計的參考，不代表其效果已在本專案得到驗證。

### 訓練、對照與驗證規劃

1. **建立傳統基準**：先完成新版 Gazebo 全路線重複測試，按感知失敗、控制偏差、安全停止等原因分類，選出最需要學習改善的部分。
2. **限定一個研究問題**：先做局部路口任務，再把模型接回完整巡邏，確認局部改善沒有降低整趟成功率。
3. **設計公平對照**：比較調整充分的純傳統方法、簡單規則式自適應方法及學習方法；使用相同感測限制、安全檢查與測試條件。以多個訓練隨機種子及重複回合呈現結果與不確定性，不只展示最佳案例。
4. **進行消融實驗**：分別移除歷史掃描、狀態資訊或學習修正，確認各設計是否真的帶來改善；安全介入次數另行統計。
5. **驗證未見情境**：改變路寬、初始位置／角度、摩擦、左右輪響應、雷達雜訊、遮擋與延遲，保留未用於調參的場景作測試。資料依場景或完整行駛回合切分，不將相鄰掃描隨機分散到訓練與測試集。
6. **驗證部署能力**：在 Xavier 量測感知到指令輸出的整體延遲、推論時間與資源使用；完成安全確認後，再進行受控實車測試。不得僅因模型較小便宣稱符合即時需求。

主要指標為完整路線成功率、碰撞與安全停止率、中心及角度誤差、操作時間、修正次數、指令平順度，以及跨場景表現。若研究感知，另量測路口誤判／漏判、幾何估計誤差與可信度的可靠性，並檢查其對完整巡邏的影響。

Gazebo 真實位置與地圖可用於訓練標籤、獎勵及評估；部署模型的輸入仍限於實車可取得的 LiDAR 與系統自身狀態，不引入底盤 odom／IMU 依賴。感測資訊不足時，學習模型也不能保證恢復可靠幾何。

可參考 [Domain Randomization](https://arxiv.org/abs/1703.06907) 的思路建立多樣化模擬條件；該研究不等於對本系統的轉移保證，適合 LiDAR 車的擾動項目與範圍仍需實驗。現有靜態射線與理想運動測試用於程式回歸，不能證明滑動、慣性或實車適應能力；相關主張須有 Gazebo 物理及相應實車證據。

### 暫定論文題目與貢獻邊界

暫定題目：**基於 LiDAR 與狀態機之窄走道巡邏機器人：結合殘差強化學習的路口操作控制**。

預期研究重點是：在不依賴底盤里程計與 IMU 的條件下，驗證受限學習修正能否改善路口操作，並以完整巡邏、跨場景測試、消融實驗及部署量測說明效果與失敗邊界。這些是待驗證的研究目標，不是既有成果；正式題目及創新性仍需透過更完整的文獻回顧與指導教授討論確認。
